# Закрыть тему и убрать за собой

Раздел навыка `anchor`. Читают, когда работа сделана и тему пора закрывать.

### Забирая работу из дерева, задавай заголовок коммита

Ветка воркера не всегда запушена: иногда он говорит «работа в дереве», иногда
забыл, иногда сессия закрылась. Тогда оркестратор забирает напрямую —
`git fetch <путь>` плюс слияние.

Git в этом случае не знает имени ветки, только путь, откуда взял, и пишет
в заголовок:

```
Merge /Users/omoto/Projects/_MEDIAOPERATOR/AZ_RAG_ALL/haq-wt/AS-2186-resolvability-gate
```

В общей истории остаётся путь на машине оркестратора. Для всех остальных это
мусор: ни номера темы, ни сути, зато полный путь к чужому каталогу.
11.10.2026 таких набралось семь за шестьдесят коммитов, заметил человек.

Правильно — задавать заголовок явно:

```
git merge FETCH_HEAD --no-edit -m "Merge <ветка>: <суть>"
```

Суть обычно уже есть в последнем коммите дерева — там номер тикета и описание.
В репозитории проекта это удобно завернуть в скрипт (`scripts/take-work.sh`):
он берёт имя ветки и заголовок из дерева сам и отказывается работать, если
забирать нечего.

Та же мысль шире: **история коммитов — общий документ**, а не журнал
оркестратора. Всё, что в ней остаётся, читают люди, у которых нет вашего
контекста и ваших путей.

### Закрыть тикет — не значит закрыть тему

Тикет в EvaTeam закрывается одной командой, и на этом легко остановиться.
Тема при этом остаётся: дерево на диске, ветка в репозитории, вкладка в
herdr, якорь в bd. 09.10.2026 так накопилось **65 рабочих деревьев**, из них
минимум девять по закрытым темам — заметил это воркер, а не оркестратор.

Чем это плохо, кроме места на диске:
- в списке вкладок не отличить живую тему от мёртвой, и оркестратор тратит
  внимание на то, чего нет;
- ветка без дерева выглядит заброшенной работой, и следующий будет гадать,
  слита она или нет;
- воркер, которому не сказали, что тема закрыта, продолжает считать себя
  занятым.

Закрытие темы — это ПЯТЬ шагов, и тикет среди них только первый:

1. **Работа слита** в main и выкачена тегом (или явно решено, что не нужна).
2. **Тикет закрыт** с итогом: что сделано, что осталось открытым вопросом.
3. **Воркеру сказано**, что тема закрыта, — иначе он ждёт.
4. **Вкладка закрыта**, дерево убрано (`git worktree remove`), ветка удалена
   после слияния.
5. **Якорь в bd закрыт**.

Пропуск любого шага оставляет хвост, который найдут через недели и не поймут,
живой он или нет.

Отдельно про шаг 4: дерево убирают ТОЛЬКО после проверки, что в нём ничего не
осталось. Две команды на каждое дерево:

    git -C <дерево> status --porcelain     должно быть пусто
    git -C <дерево> log origin/main..HEAD  должно быть пусто

Первая ловит незакоммиченное, вторая — закоммиченное, но не слитое. Пропуск
второй стоит дороже: незакоммиченное хотя бы видно глазами в каталоге, а
коммит в неслитой ветке исчезает вместе с деревом бесследно.

09.10.2026 уборка 65 деревьев по этому правилу нашла ДВЕ несданные работы —
починку замера эталона и проверку гипотезы по кэшу, обе закоммичены и обе не
слиты. Воркеры их сделали и не сказали; без проверки обе ушли бы в никуда.

Чего при уборке НЕ делать:
- **не `rm -rf` по каталогу дерева** — `git worktree remove` знает про
  служебные ссылки, прямое удаление оставляет записи в `.git/worktrees`;
- **не удалять ветку принудительно**, пока не убедился, что она слита:
  `git merge-base --is-ancestor <ветка> origin/main` отвечает на это точно, а
  «вроде сливали» — нет;
- **не убирать дерево, где работа идёт прямо сейчас**. Свежее время
  последнего коммита — признак живой темы, а не забытой.

Уборку делают периодически, а не только при закрытии темы: временные деревья
под мелкие правки («поправить линт», «вернуть файл») копятся незаметно и
ничем не отличаются от рабочих, пока их не пересчитать.

## Свести и закрыть

Путей два, и выбирает не оркестратор, а происхождение работы.

**Ветку вернула сессия** — сводят локально, без merge request. Проверку
прогоняет оркестратор: выкачивает ветку в отдельный worktree и запускает то,
что гоняет CI. Лишний круг через интерфейс тут ничего не добавляет: обе
стороны — свои же сессии, обсуждать в комментариях некого.

**Ветку прислал сотрудник** — принимают через merge request. Он даёт то, чего
локальное слияние не даёт: пайплайн на самой ветке, страницу с историей и,
главное, **запись о том, кто принял и когда**. Для проекта под квалификацией
это не формальность — приёмку чужой работы нужно уметь предъявить.

Проверять всё равно локально, а не доверять зелёному пайплайну: он гоняет то,
что настроено, а не то, что нужно этой правке.

**Ветку с открытым PR не переименовывать на GitHub.** PR при этом не
переезжает на новое имя, а закрывается — 02.10.2026 так разом закрылись
четыре PR. Id якоря достаточно в ЛОКАЛЬНОМ имени ветки: хук читает его, а
upstream может называться как угодно (`git branch -u origin/<старое-имя>`).
Если уже случилось — вернуть старое имя пушем `<новое>:refs/heads/<старое>`
и `gh pr reopen`.

**Ветку при слиянии НЕ удалять.** В merge request галочка «Delete source
branch» стоит по умолчанию — её снимают. Две причины.

Ветки не удаляются вовсе, а помечаются `merged/` или `archived/`: имя говорит,
чем тема кончилась, и работа остаётся восстановимой. Удаление эту разметку
обходит молча.

Вторая причина обнаружилась 29.09: задание сборки, поставленное в очередь до
слияния, добирается до бегунка уже после — и падает с `couldn't find remote ref
refs/heads/<ветка>`. Работа при этом влита и цела, но в истории остаётся
красное задание, в котором завтра кто-то будет искать дефект. Гонка очереди с
удалением ветки создаёт ложную тревогу на ровном месте.

### Слияние PR тем: пара на свежем main, по одной

Так сводят темы, которые воркер сдал PR (`worker-done`), — в том числе темы
из двух репозиториев, фронт + бэк. Сливает **только оркестратор**: воркеру
это в постановку не пишут, а ограда воркера не пускает ни `gh pr merge`,
ни `anchor-merge`, ни `anchor-queue run`.

```bash
anchor-merge <якорь> <репо-бэка>:<PR> <репо-фронта>:<PR>     # пара
anchor-merge <якорь> <репо>:<PR> --check-only                 # проверить, не сливать
anchor-merge <якорь> <репо>:<PR> --migration <имя> --backup <копия базы>
```

Порядок, и почему он такой:

1. **Пара проверяется вместе поверх свежего `origin/main`** обоих
   репозиториев — во временных деревьях, а не в основном и не в дереве
   воркера. Ветки тем ответвлялись от main часами раньше; проверять их «как
   есть» значит проверить не то, что окажется в main. Тесты бэка видят
   временное дерево фронта (`{tree:…}` в гейтах).
2. **Только известные падения.** Красный прогон допустим, если каждое
   падение — из списка `[known]` в `.anchor/gates`. Новое — стоп, на
   доработку. Гейты читаются с `origin/main`, а не из PR: правка не
   ослабляет собственную проверку.
3. **Строго по одной.** Блокировка на машину: второй прогон ждёт первого.
   05.10.2026 два параллельных прогона делили временные деревья и сорвали
   друг друга. Причина и по смыслу: вторая тема проверяется поверх main, в
   который уже влита первая. main уехал за время проверки — стоп, перепроверка.
4. **Ждать — по выходу процесса**, а не по строке в журнале. Оркестратор
   запускает `anchor-merge` фоновой командой, уведомление приходит с кодом
   выхода (0 — слито, 1 — нет) и `result.json` в каталоге журналов.
   05.10.2026 связка ожиданий через поиск строки в логе сработала по строке
   прошлого прогона.
5. **Squash**, ровно проверенного коммита (`--match-head-commit`). Пара —
   бэк первым. Слился один из двух — итог «СЛИТО ЧАСТИЧНО», разбирать руками.
6. **Миграции — только оркестратор и только после копии базы.** Скрипт
   миграций не применяет: сначала копия, потом применение, потом
   `anchor-merge --migration <имя> --backup <файл копии>`; без копии — отказ.
7. **Ветки не удалять, а переименовывать в `merged/…`** — скрипт делает это
   после слияния (переименование уже слитого PR не закрывает).

Гейты — в репозитории, `.anchor/gates` (формат — `anchor-merge --help`):

```ini
[gates]
base = main
test = .venv/bin/python -m pytest tests -q -p no:cacheprovider
test.failures = ^(FAILED|ERROR)\s
typecheck = node_modules/.bin/tsc -b
build = npm run build

[known]
test_tool_company_binding

[env]
AI_OFFICE_FRONTEND = {tree:ai-office-frontend}

[link]
node_modules = /home/develop/projects/wt/_shared-front/node_modules
```

Нет файла гейтов — нет слияния: проверять нечем. Каждая команда идёт через
`heavy`.

### Слияние локальной ветки

1. Прогнать то, что проект считает проверкой (тесты, сборка).
2. Слить в `main`. **Осторожно:** обычный `git merge` в основном дереве падает,
   если рабочее дерево грязное, а среди изменений есть симлинк на каталог —
   git отказывается сохранять состояние («is beyond a symbolic link»). Обход:
   сделать merge во временном worktree и перемотать `main` на результат
   (`git merge --ff-only <коммит>`).
3. Убрать за собой: `herdr worktree remove`, ветку переименовать в
   `merged/<ветка>` (не удалять — см. выше), закрыть якорь
   (`bd close <id> --reason="…"`), закрыть вкладку.

### После слияния

**Влито — не значит сделано.** Слияние закрывает ветку, а не тему. Если работа
должна оказаться на машине — роль, юнит, образ, настройка, — тема живёт до
применения и проверки на месте, и якорь остаётся открытым. 02.10.2026 так
закрывали две темы: первую — после реального применения (проверены вход в
реестр, разложенные файлы, живой сервис), вторую намеренно оставили открытой:
код в основной ветке, но роль ещё не применена, а критерий приёмки говорит о
состоянии машины, а не о содержимом ветки.

Отсюда и признак, по которому убирают за собой: панель и каталог темы
закрывают, когда ветка влита И за ней не числится незавершённого применения.
«Когда вспомню» — не признак: 01.10.2026 две панели провисели сутки после
слияния, и заметил это человек, а не оркестратор.

Пункт 3 пропускают чаще всего — и тогда каталоги слитых веток висят месяцами.
