# Что видно оркестратору, а что нет

Раздел навыка `anchor`. Читают, когда кажется, что воркер молчит, или перед закрытием темы.

### Межсессионные сообщения теряются — читают панель

Воркер пишет оркестратору, сообщение уходит на одобрение владельца машины и
через какое-то время **истекает, не дойдя**. 08.10.2026 так пропали четыре
сообщения подряд: воркер отчитывался о работе, исправлял собственную ошибку,
просил деревья — оркестратор не получил ни одного и считал, что воркер молчит.
Выяснилось случайно, когда владелец скопировал его экран в чат.

Отсюда два правила, и оба обязательны.

**Оркестратор читает панель, а не ждёт сообщений.** `herdr agent read <имя>`
показывает, что воркер на самом деле написал. Проверять панели тем, от которых
ждёшь ответа, — часть обхода, а не действие по настроению. «Воркер молчит» без
проверки панели — утверждение, не факт.

**Воркер пишет результат в тикет, а не только оркестратору.** Сообщение может
не дойти; тикет переживает и доставку, и смену сессии. В сообщении — «готово,
подробности в тикете», в тикете — сами подробности. Это заодно решает задачу,
которая возникнет позже: через месяц никто не будет искать результат в чужой
переписке.

Задачи воркеру оркестратор ставит через `herdr agent prompt <имя> "<текст>"` —
этот путь прямой и одобрения не требует.

**Воркер пишет оркестратору тоже через `herdr agent prompt`, а не через
`SendMessage`.** Оркестратор, поднятый в панели herdr, для `SendMessage`
невидим: имя `proj-orchestrator` есть только в herdr, а `ListAgents` показывает
сессии под своими именами (`proj-repo-ab` и т. п.), по которым не понять,
кто из них оркестратор. 14.10.2026 воркер bm-migrate отправил отчёт по фазе
через `SendMessage({to: "proj-orchestrator"})` и получил «No agent named
'proj-orchestrator' is reachable». Дошло только через
`herdr agent prompt proj-orchestrator "<текст>"`: ответ херд вернул как
`agent_prompted`. Порядок такой:

```bash
herdr agent get <оркестратор>                  # имя верное, панель жива
herdr agent prompt <оркестратор> "<итог: что сделано, чем проверено, что решить>"
```

Первая строка сообщения должна читаться отдельно: «Ответ от <тема>: …».
Это вопрос или отчёт по ходу работы. Сдача темы по-прежнему идёт через
`worker-done`, подробности — в тикет.

### Оркестратор не знает, что у воркера готово

`herdr agent list` отвечает на вопрос «кто есть» и отвечает верно. Но
оркестратору нужен другой: **у кого лежит работа, которую я ещё не забрал**.

09.10.2026 работа трижды находилась в дереве ПОСЛЕ того, как тема считалась
закрытой. Воркер доделал и не сказал; межсессионное сообщение не дошло;
оркестратор видел «idle» и шёл дальше. Один раз это была готовая правка,
найденная случайно при уборке — она бы исчезла вместе с деревом.

Источников три, и порознь каждый говорит правду:

- **herdr** — какие панели живы и чем заняты;
- **git** — что лежит в деревьях: несливённое и незакоммиченное;
- **трекер** — в каком состоянии тикет. Код тикета берётся из имени ветки по
  шаблону `ANCHOR_TICKET_RE` (по умолчанию `ABC-123`), состояние — командой
  `ANCHOR_TICKET_STATUS_CMD` с `{code}`; без неё — каталог `get-tickets`
  (EvaTeam), если он есть, иначе в колонке только код.

Расходятся они молча. `scripts/anchor-status` сводит их в одну таблицу:

```
воркер      ветка                не слито  не закоммич  состояние  тикет
tkt-2209    TKT-2209-review-queue       0            1  idle       TKT-2209 IN_PROGRESS ←
merge-gate  TKT-2022-merge-gate         1            0  idle       TKT-2022 IN_PROGRESS ←

ДЕРЕВЬЯ БЕЗ ВОРКЕРА — работа есть, сказать о ней некому:
  TKT-2182-parent-window         не слито 0, не закоммичено 3

ЗАБРАТЬ: merge-gate
```

Стрелка отмечает то, что ждёт оркестратора. Отдельный раздел — деревья,
за которыми никого не осталось: их содержимое не всплывёт само никогда.

Смотреть: перед закрытием темы, раз в час-полтора работы с несколькими
воркерами, и всегда, когда кажется, что воркер молчит. Скрипт только читает.

**Почему не завести для этого четвёртый источник** (bd, файл состояния,
что угодно ещё): сегодняшние потери произошли не от нехватки источников, а
от их расхождения. Ещё один разойдётся с остальными тремя и добавит к
вопросу «где правда» четвёртый ответ.

### Читать результат

```bash
herdr agent get tkt2119
herdr agent read tkt2119 --source recent-unwrapped --lines 200
```

### Когда пошло не так

Три исхода, и ни один не значит «повторить отправку».

**`blocked`** — воркер стоит на вопросе или запросе разрешения. Посмотреть, на
чём именно (`agent read`), и **спросить человека**. Отвечать за него на диалог
разрешения оркестратор не вправе: это обход того самого места, где человек
решает.

**`agent_prompt_stalled`** — отправка прошла, активности не видно. **Не слать
повторно вслепую:** неудачное ожидание не доказывает, что промпт не доехал.
Сначала `agent get` и `agent read`.

**`timeout`** — истекло время вызывающего. То же правило: сначала посмотреть,
потом решать.
