# Решения, на которых стоит схема

Записано 22.09.2026 по итогам разбора. Каждое решение — с причиной: без причины
решение через полгода выглядит произволом, и его отменяют первым.

## Что болело

Четыре сессии Claude Code шли параллельно по разным темам. В один день:
`main` трижды уехал под руками, слияние двух параллельных веток пришлось делать
вручную, а merge подсунул устаревшую версию чужого теста. В базе задач 268
записей и ни одного места, отвечающего на вопрос «что сейчас в работе».

Названы две боли: **сессии дерутся за файлы** и **не видно общей картины**.

## Якорь

**Тема крепится к якорю в beads** — эпику, если тема большая, или одиночной
задаче, если она одна. Не к ветке, не к вкладке, не к проекту в CRM.

Почему: якорь — единственная вещь, которая переживает сессию. У него есть дети,
зависимости, история закрытий и причины. Ветка и вкладка становятся
производными: их имена берутся из якоря, а не наоборот.

Почему не «всегда эпик»: большинство из 268 задач живут без эпика. Правило,
заставляющее плодить эпик из одной задачи ради формы, обходят первым.

## Сессия — расходник

**Состояние живёт в трекере, а не в контексте сессии.** Сессий может быть
сколько угодно; любая поднимает нужный контекст из beads.

Почему: «одна сессия вместо четырёх» лечит симптом. Дерутся не окна — дерётся
состояние, которое помнит только процесс. Когда помнит трекер, число окон
перестаёт иметь значение.

## Два трекера, ноль синхронизации

**beads** — инженерные задачи по коду. **ai-o (CRM)** — клиенты, сделки, деньги.
Связь односторонняя: в якоре beads лежит ссылка на проект ai-o, и всё.

Почему не синхронизировать: двусторонняя связь без синхронизации обманывает —
одна сторона молча устаревает. В этом проекте так уже случилось: файл
`issues.jsonl` выглядел записью задач, застыв на 46 записях из 268.

Ссылка необязательная: у большинства инженерных якорей пары в CRM нет, а
обязательное поле даёт ссылки «лишь бы заполнить» — они хуже отсутствующих.

## Worktree на тему

**Каждая тема живёт в своём git worktree и своей ветке.** `main` — только для
сведения.

Почему: в день разбора два параллельных процесса не столкнулись ровно потому,
что каждый сидел в своём worktree. Общий `main` за то же время уехал трижды.

Цена названа честно: worktree не получает `.env`, `.venv`, `node_modules` —
их надо линковать при создании. Забыть это стоит минуты выяснения, почему в
каталоге не запускаются тесты.

## Якорь определяется по ветке

Имя ветки уже содержит id (`feature/aio-ppku-jobs-queue` → `aio-ppku`).

Почему не файл-маркер в каталоге: это второй источник правды, который однажды
разойдётся с веткой. Ветка на worktree одна, и незаметно переименовать её нельзя.

## herdr делает половину работы

`herdr` (terminal workspace manager) уже умеет: именованные сессии и вкладки,
привязку вкладки к uuid сессии Claude Code и каталогу, статусы `idle/working/done`,
`worktree list/create/open/remove`, а также межсессионное общение —
`herdr agent prompt`, `wait`, `read`.

Поэтому своей команды входа почти не нужно: нужна тонкая обвязка, которая
добавляет к herdr то, чего он не знает, — beads.

**Чего herdr не делает:** не связывает вкладку с якорем, не готовит окружение
в новом worktree, не убирает за закрытым якорем вкладку и каталог.

## Имя вкладки — из якоря

Хук при старте сессии определяет якорь по ветке и переименовывает вкладку в его
заголовок.

Почему не руками: имена, поставленные руками, уже разошлись с работой — из
четырёх открытых вкладок с задачами совпадала одна. Имя остаётся человеческим:
берётся заголовок якоря, а не id.

## dispatch — исполнитель, а не память

Скилл `dispatch` (bassimeledath/dispatch): главная сессия держит чеклист,
фоновые воркеры выполняют пункты со своими полными контекстами, вопросы воркера
доходят до человека через IPC.

**Он исполняет, помнит beads.** План выводится из открытых детей якоря, каждый
пункт заканчивается закрытием задачи. Воркер всегда в worktree — в самом скилле
это директива, о которой надо вспомнить, а значит однажды забудут.

Почему вообще к нему вернулись: он не был отвергнут — просто выпал из обихода
(41 задача в `.dispatch/tasks`, последняя активность 19.06). Его июньские планы
уже ходили в beads командами `bd update --notes` и `bd close`, то есть связка
проверена на практике.

## Сессии говорят друг с другом, решения пишут в трекер

`herdr agent prompt` и `wait` позволяют попросить соседнюю сессию проверить
результат или дождаться её завершения. Но **что бы сессии друг другу ни сказали,
решение записывается в beads** — иначе договорённость живёт в памяти двух
процессов и исчезает вместе с ними.

## Схема личная, не командная

beads лежит в `.beads/dolt`, в git не версионируется, копия — только в ветке
`beads-backup` по ручной команде. Для команды такое хранилище не годится.

Решено: схема для одного человека; команда видит результат в CRM, а не ход
работы. Общий трекер «на будущее» пришлось бы содержать сейчас, а пользоваться
им — неизвестно когда.

## Что осталось за границей

- Cowork Dispatch (фича Claude Desktop): его сущности эфемерны — дочерняя задача
  живёт в сайдбаре приложения, а не в трекере, и на вопрос «что осталось» по-
  прежнему нельзя ответить командой. Он про «поставить работу и уйти», а не про
  «держать тему месяцами».
- Экран «что в работе» внутри продукта: beads не виден серверу, раздел потребует
  отдельного канала выгрузки. Пока картина нужна одному человеку, команда дешевле.

## Оркестратору хук тоже что-то должен

Хук печатает блок якоря, только если идентификатор читается из имени ветки.
В основном дереве ветка `main`, якоря нет — и хук выходит сразу после ядра.

Получалось, что оркестратор — единственная роль, которой схема не даёт ни
инструмента, ни команды. Ядро говорит «темы живут в worktree», но не называет
`herdr`: и не должно, ядро про продукт, а не про инструментарий. Навык `anchor`
называет, но вызывается вручную — то есть до сессии, которая о нём не знает,
не доходит.

29.09.2026 это выстрелило: оркестратор завёл тему через `git worktree add`
и отдал работу сообщением. Каталог появился, вкладка нет, статус исполнителя
в `herdr agent list` не отражался. Оба отказа молчаливые — ничего не упало,
просто спейса у темы не было, и человек спросил, почему.

Поэтому хук в основном дереве печатает короткий блок с двумя командами и
ссылкой на навык. Не процедуру целиком — процедура в навыке; ровно столько,
чтобы сессия знала, что инструмент есть и как он называется.

## Два пути приёмки, и выбирает происхождение работы

Схема описывала только локальное слияние: исполнитель возвращает ветку,
оркестратор сводит. На практике рядом жил второй порядок — merge request, — и
какой применять, решалось каждый раз заново.

Решено 29.09.2026 оставить оба и развести по источнику. Ветка от своей же
сессии сводится локально: круг через интерфейс ничего не добавляет, обсуждать
в комментариях некого. Ветка от сотрудника принимается через MR — он даёт
пайплайн на ветке, страницу с историей и запись о том, кто принял и когда.
Последнее весит больше остального: проект идёт под квалификацию, и приёмку
чужой работы нужно уметь предъявить.

Проверка в обоих случаях локальная. Зелёный пайплайн говорит, что прошло
настроенное, а не что правка верна.

## Оркестрация была описана наполовину

Схема учила, как отдать работу соседней сессии, но не как её породить: ни
`pane split`, ни `agent start` в ней не было. Оркестратор, не знающий этих
команд, делает то же, что сделал бы любой — заводит worktree через git и пишет
соседу мимо herdr. Каталог появляется, панели нет, статуса в `agent list` нет.

Заодно нашлась ошибка в совете. Схема предлагала `agent prompt --wait --until
idle`, а `--wait` и так ждёт первое устоявшееся из трёх — `idle`, `done`,
`blocked`. С `--until idle` ожидание пропускает и честно ответившего воркера в
`done`, и застрявшего в `blocked`, и отваливается по таймауту там, где всё уже
случилось. Документ при этом двумя абзацами ниже сам писал «финальных состояний
два» — то есть противоречил собственному примеру.

Отдельным разделом записано, чего herdr не делает: он мультиплексор
терминальных агентов, а не движок рабочих процессов. Дробление, передача
результата, признак готовности, поведение при провале и изоляция — логика
оркестратора, и её пишет человек поверх. Без этой границы herdr выглядит как
инструмент, который «сам всё оркеструет», и от него ждут того, чего он не
обещает.

## Хук чинит окружение темы, а не только сообщает о нём

Схема знала про неполное окружение worktree и лечила его указаниями человеку:
слинкуй `.env`, проверь `BEADS_DIR`, поправь путь хука. Указание, которое надо
помнить при каждом новом дереве, рано или поздно забудут — и забыли: 29.09.2026
все три дерева тем печатали «Hook script appears to be missing» при каждой
остановке сессии, а `brain-capture` не работал в темах вовсе.

Разница между двумя отказами существенна. `BEADS_DIR` хук уже правил сам, и
проблемы с ним не было. Путь хука он не трогал — и именно он сломался.

Теперь хук нормализует и его: переписывает `$CLAUDE_PROJECT_DIR` на абсолютный
путь основного дерева, но ТОЛЬКО там, где подстановка ведёт к несуществующему
файлу. Скрипт лежит в дереве — значит его туда положили намеренно, не наше дело.
Чужие ключи в `settings.local.json` при этом не трогаются.

Ограничение честное: настройки читаются при старте сессии, поэтому правка
догоняет следующую сессию, а не текущую. Состояние сходится, но не мгновенно.

## Раздал — поставь будильник; воркеров — сколько выдержит машина

03.10.2026, один день, два провала одного корня: оркестратор относился к
воркерам как к процессам, которые «сами придут».

Первый — ресурсы. Десять воркеров разом на 4 ядрах и 8 ГБ: каждая сессия
поднимает свои MCP-плагины (браузерный — ~300 МБ), а проверки идут
одновременно. OOM-killer 17 раз, убиты в том числе соседние сервисы. Схема не
говорила ни сколько воркеров можно, ни как их облегчить. Теперь говорит:
выключать ненужные плагины в дереве темы, тяжёлое — через очередь `heavy`,
добавлять по одному под замер, потолок — по процессору, а не по числу тем.

Второй — ожидание. После облегчённого перезапуска три воркера закончили и
открыли PR за полчаса до того, как это заметил оркестратор: он раздал работу
без `--wait` и ничего не поставил ждать. herdr сам не будит, а намерение
«проверю, когда отчитаются» механизмом не является. Теперь раздача и
ожидание — одно действие: фоновое `herdr agent wait` на каждого воркера,
окончание приходит уведомлением.

Сюда же — урок 02.10: переименование ветки на GitHub закрывает её открытый
PR, а не переносит. Id якоря держат в локальном имени ветки.

## Головы не темы, но живут в той же панели

05.10.2026. Схема знала только темы, а на сервере жили и головы: продавец со
своим ботом, клиентский бот, оркестратор поверх трёх репозиториев. Три
провала за два дня, все от того, что для них не было места в схеме.

Продавец после перезагрузки сервера двое суток молчал: панель herdr пережила
рестарт, агент — нет, и никто не знал, что его надо поднимать. Оркестратор
жил в tmux внутри панели herdr, и herdr его не видел: ни `agent list`, ни
`agent prompt`. А боковая панель показывала головы россыпью на верхнем уровне,
отдельно от оркестратора, которому они подчинены.

Решения. Головы — полноправные агенты herdr, без tmux, с именем; после
рестарта их поднимают `agent start` в ту же панель. Чтобы они стояли под
оркестратором, — `scripts/heads-nest`: пустой репозиторий-родитель и связанное
дерево на голову, потому что herdr группирует воркспейсы по связанным деревьям
одного репозитория и ни по чему больше.

Цена названа честно: это опора на поведение herdr, а не на его обещание;
уровней вложенности два; команды herdr для деревьев видят подставное дерево.
Поэтому скрипт необязательный, как `heavy`, а темы им без нужды не накрывают —
у них вложенность по своему репозиторию правильная и так.

Отказ `agent start` с `agent_not_ready` оказался ложным: агент жил, только без
имени. Лечится `agent rename`, а запасной второй запуск дал бы два процесса
на одну сессию и два поллера на одного бота.

## Gas Town не берём; берём из него четыре идеи

05.10.2026 сравнили схему с Gas Town (steveyegge/gastown) — оркестратором
воркеров Claude Code поверх того же beads. Решение Кирилла: целиком не
переходить, взять четыре механизма и сделать их поверх herdr.

Почему не целиком:

- **tmux прячет агента от herdr.** Gas Town держит воркеров в tmux. Это уже
  проверено на себе: оркестратор, живший в tmux внутри панели herdr, для
  herdr не существовал — ни `agent list`, ни `agent prompt`, статус
  `unknown`. Вся видимость тем, ради которой схема заводилась, держится на
  herdr.
- **Воркеры без ограды.** Его воркеры работают без вопросов о разрешении, и
  необратимое ничем не закрыто. У нас тот же режим включён только вместе с
  `worker-guard`, и без него не включается.
- **Тяжёлый служебный слой на 8 ГБ.** Демоны, сторож, Dolt-сервер — постоянная
  цена в памяти на сервере, где десять воркеров уже вызвали OOM-killer 17 раз.
  Здесь служебный слой — четыре скрипта без демона: работают, только когда
  их зовут.
- **Одна задача — один репозиторий.** Его единица работы живёт в одном
  репозитории. Наши темы — часто пара фронт + бэк и сливаются парой; разрезать
  их на две задачи значит потерять проверку вместе.

Что берём:

- **`gt done` → `worker-done`.** Готовность объявляет воркер, а не угадывает
  оркестратор по статусу herdr: `done` приходит и при живой фоновой сборке.
  Маркер `.anchor/done.json` со временем внутри: старый маркер не срабатывает
  как новый.
- **Пульс воркера → `worker-state`.** Но без сторожа-убийцы: в Gas Town упор в
  лимит использования принимали за зависание и убивали здоровых воркеров.
  «Застрял» у нас — только по двум признакам (слова воркера и неработающий
  терминал), молчание — повод прочитать панель, и скрипт ничего не
  останавливает.
- **Потолок `max_polecats` → `anchor-queue`.** Очередь в каталоге, потолок
  `ANCHOR_MAX`, без демона: `run` зовёт оркестратор в фоне. Потолок — замер
  03.10 (три воркера на 4 ядра / 8 ГБ), а не число тем.
- **`merge_queue.*_command` → `.anchor/gates` + `anchor-merge`.** Гейты — в
  репозитории, процесс — общий: обобщение нашего `aio-mergepair`. Гейты
  читаются с `origin/main`, а не из PR, чтобы правка не ослабляла собственную
  проверку.

## Слияние — одно, по одной, по выходу процесса

Процесс сведения PR жил в скрипте `aio-mergepair` и в памяти оркестратора:
пара PR (фронт + бэк) поверх свежего main во временных деревьях, только
известные падения, squash, миграции — после копии базы, ветки — в `merged/…`.
05.10.2026 он сорвался не на проверке, а на обвязке: два прогона, запущенные
параллельно, делили одни временные деревья и сорвали друг друга, а ожидание
окончания, связанное поиском строки в общем логе, сработало по строке
прошлого прогона.

Решено: последовательность держит блокировка в самом `anchor-merge`, а не
дисциплина; конец прогона — выход процесса с кодом и `result.json` в своём
каталоге журналов, а не строка в общем. Между проверкой и слиянием main
сверяется ещё раз: уехал — стоп, иначе слито было бы не то, что проверено.
Сливается ровно проверенный коммит (`--match-head-commit`).

Слияние — работа только оркестратора. В постановке воркеру оно не
упоминается; ограда воркера не пускает `gh pr merge`, а `anchor-merge` и
`anchor-queue run` должна не пускать тоже — правка ограды за оркестратором.
